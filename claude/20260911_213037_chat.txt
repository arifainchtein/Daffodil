## What I found

**Pulled TopTank's history from the `teleonome` DB on ChinampaMonitor** (day-by-day, first reading of each day, back to May). Here's the picture:

- **Through Sep 2**, everything looked sane: `Battery Voltage` 2.8–3.3V (right for a LiFePO4), `Panel Voltage` swinging 0.05V (night) up to 5–6V (daytime sun) — exactly what a USB-terminated panel should do, `V50 Voltage` ~3.35V.
- **First sample of Sep 3, 00:01:52** — it flips, hard, and stays flipped every single day since:
  - `Panel Voltage` = exactly **35** on every sample, every day, regardless of current (which itself varies normally, 34–344mA) — not drifting, not noisy, a dead flat constant.
  - `V50 Voltage` = exactly **0** on every sample, every day.
  - `Battery Voltage` climbed out of the correct range — today it's running 4.97–5.22V under load (physically impossible for a 3.2V LiFePO4 cell).

That's not gradual hardware drift — a real ADC/sensor fault wobbles. A value pinned at exactly the same number for 9 days straight across varying load is a firmware/I2C-state signature.

**Timing is the smoking gun**: the break lands right on top of `65bd814 Release v38` (2026-09-02 12:23) and `28d1825 fix port 18` (2026-09-02 14:24) — TopTank's Sep-3 00:01 sample is ~10 hours after those commits. It was almost certainly reflashed with that build that evening.

**Code-level explanation for the two symptoms:**
- `V50 Voltage` is read unconditionally in `readSensorData()` (`Daffodil.ino:2281-2283`, `ADS.readADC(3)`) with no `foundADS` guard — if the ADS1115 stops answering on I2C, this silently returns 0. That matches exactly.
- `Panel Voltage` comes from `solarIna219.getBusVoltage_V()` (0x45), gated on `foundINA219Solar` being true — so that chip *is* still being detected, but its register reads are coming back as a stuck, wrong value. That's the classic signature of a wedged I2C bus (one device — likely the now-silent ADS1115 at 0x48 — hanging SDA/SCL), which would also explain the elevated battery voltage from the 0x41 INA219 on the same bus.

**Important**: I diffed everything from that point through the current HEAD (`5da9f4e Release v40`, Sep 3 07:38) — nothing touches the ADS1115/INA219/I2C code in between. So flashing v40 as-is will **not** fix this by itself; the regression is already baked in and unaddressed.

I don't have physical/USB access to TopTank from here to pull a live `debug#1` boot log and confirm which chip is actually wedging.
