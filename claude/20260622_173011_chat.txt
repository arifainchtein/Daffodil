Good challenge — here's the honest answer:

The only real reason to have two structs is **storage efficiency** — `CommaRecord` stored to flash doesn't need `totpcode`, `index`, `total`, or `checksum`, so those 7 bytes would be wasted per record × 650 = ~4.5KB of zeros on flash. But with LittleFS on ESP32 with a 1MB+ filesystem, that's negligible.

Against that, you get: simpler code (no copy/wrap step), one mental model, fewer bugs. That tradeoff clearly favours one struct.

The merged design, with serialnumber added:

```c
#pragma pack(push, 1)
struct CommaRecord {
  uint32_t time;           // Unix-seconds of reading
  float    voltage;        // battery voltage
  char     devicename[8];  // device short name
  uint8_t  serialnumber[8];// device serial number
  long     totpcode;       // TOTP auth (0 when stored, set before LoRa send)
  uint8_t  index;          // 0-based batch position (set before LoRa send)
  uint8_t  total;          // total records in batch (set before LoRa send)
  uint8_t  checksum;       // XOR checksum (set before LoRa send)
};
#pragma pack(pop)
// sizeof = 4+4+8+8+4+1+1+1 = 31 bytes on ESP32
```

31 bytes is unique vs all existing LoRa packet sizes (19, 37, 164, and DigitalStablesData which is 200+).

The `index`/`total` fields feel like batch metadata but in practice every record you send already *is* one packet, so knowing its position in the sequence belongs on the record. When stored, those bytes are just 0 — harmless.

## What's working
- **Annabelle sends correctly**: `Annabelle.ino:1049-1080` triggers every 5 minutes (`minute % 5 == 0`), downloads from OpenWeatherMap if internet is up, builds a `WeatherForecastUpdate` (4 forecasts + TOTP), and calls `sendMessage()`.
- **Daffodil's dispatch is correct**: `Daffodil.ino:526-540` matches on `sizeof(WeatherForecastUpdate)`, validates the TOTP code, and calls `weatherForecastManager->saveForecasts(weatherForecastUpdate.forecasts)`.
- **Radio config matches** on both ends (433MHz, SF9, BW125kHz, same sync word default).
- **TOTP scheme is a shared network-wide secret** (not per-device-pair), so that's not a v1 vs v2 mismatch issue — though it does depend on RTC clock sync between the two devices (worth checking if either device's time has drifted).

## The bug
`WeatherForecastManager::saveForecasts()` (`WeatherForecastManager.cpp:164-180`) is declared and implemented to take **8** `WeatherForecast` elements — `memcpy(forecasts, newForecasts, sizeof(WeatherForecast) * 8)`, i.e. it always reads/writes 320 bytes.

But the LoRa-transmitted struct only carries **4** forecasts (`WeatherForecastUpdate.forecasts[4]` in `SolarPowerData.h:23` — kept at 4 instead of 8 specifically to fit LoRa's payload size limit).

So `Daffodil.ino:533` calls `saveForecasts(weatherForecastUpdate.forecasts)` with only a 4-element (160-byte) array, and `saveForecasts()` reads 320 bytes from it — a **160-byte stack over-read** past the end of the local `weatherForecastUpdate` variable in `processLora()`, every single time Daffodil receives a forecast packet. The first 4 slots (`forecasts[0..3]`, including the one actually used for the cloudy check, `forecasts[0].cloudiness`) get the correct data, but slots `[4..7]` get garbage stack memory, and that garbage also gets written to NVS via `preferences.putBytes()`.

This is the only call site affected — Annabelle's own `downloadWeatherData()` (`WeatherForecastManager.cpp:159`) correctly passes its real 8-element member array.

This bug doesn't fully explain "not receiving at all" (since forecast[0] — the one Daffodil actually reads — is correctly copied), but it is definite undefined behavior on every reception, and on ESP32 stack overreads of this size can occasionally trigger crashes/resets depending on stack layout, which **would** look like "never receiving" if it crashes before the debug log prints.

## Recommended next steps
1. **Fix the over-read**: add a `saveForecasts(const WeatherForecast newForecasts[], int count)` overload (or change the existing one to take a count) so Daffodil's 4-forecast LoRa packet doesn't get read as 8. This is in the shared library, so it'd affect both Annabelle and Daffodil builds.
2. **Confirm with live debug serial** (`debug#1` on both devices) whether Daffodil ever logs `" Receive and processed weatherForecast "` (success) or `" Receive WeatherForecastUpdate but invalid code"` (TOTP/clock-drift rejection) — that tells us definitively whether packets are arriving at all vs. being rejected vs. corrupting the device.
