So 3.3V now is mid-charge (LiFePO4's discharge curve is very flat, so voltage alone doesn't map cleanly to %, but 3.3V is comfortably "not empty, not full" — full/charge-termination is ~3.6V).

**On the 16mA vs 130mA question** — I don't think it's a sun/battery blend, and here's why: V50 is fed by two sources that are diode-OR'd, not blended:
- **D2** passes panel power straight through from V50_I when the panel is strong enough.
- **U5 (boost)** takes VBAT in and pushes it up to a fixed regulated output on V50, only when **MAX809L** (U6) detects V50_I has sagged below its ~4.63V threshold — and once boost is driving V50 to its regulated level, that reverse-biases D2, so the panel path drops out entirely.

It's a hard switch between "panel powers everything" and "battery powers everything," not a proportional mix. Given V50_I is reading ~3.4V right now (well under 4.63V), the boost is almost certainly active, which means **the battery should be supplying the entire V50 load right now — including during transmit — not just the difference.**

     ```cpp
     #define DIAGNOSTICRECORD_H

     // Generic on-demand diagnostics, triggered remotely via a RequestCommand
     // ("EnableDiagnostics#<type>" / "DisableDiagnostics") — NOT part of the normal periodic
     // uplink. diagnosticType selects which member of the payload union is populated; add new
     // diagnostic kinds by adding a payload struct + union member + DIAGNOSTIC_TYPE_* constant,
     // not a new top-level LoRa packet type/size.
     #define DIAGNOSTIC_TYPE_NONE        0
     #define DIAGNOSTIC_TYPE_TX_CURRENT  1

     #define DIAGNOSTIC_TX_MAX_SAMPLES 20

     #pragma pack(push, 1)
     struct TxCurrentSample {
         uint16_t offsetMs;    // ms since LoRa.beginPacket()
         uint16_t milliamps;   // INA219 current_mA at that offset
     };

     struct TxCurrentDiagnosticPayload {
         uint16_t v50i_mV;     // V50_I sampled just before keying up, millivolts
         uint16_t mAPre;       // battery current just before keying up
         uint16_t mAPost;      // battery current just after TX completed
         uint8_t  sampleCount; // valid entries in samples[]
         TxCurrentSample samples[DIAGNOSTIC_TX_MAX_SAMPLES];
     };

     // Total size: 4 (totpcode) + 8 (serialnumberarray) + 1 (diagnosticType)
     //           + 87 (payload union, sized to TxCurrentDiagnosticPayload) + 1 (checksum) = 101 bytes.
     // Must stay unique relative to other LoRa packet structs (DigitalStablesData, RequestCommand,
     // WeatherForecastUpdate, GraveyardShiftUpdate) since receivers dispatch on packet size.
     struct DiagnosticRecord {

         uint8_t serialnumberarray[8];
         uint8_t diagnosticType = DIAGNOSTIC_TYPE_NONE;
         union DiagnosticPayload {
             TxCurrentDiagnosticPayload txCurrent;
             DiagnosticPayload() : txCurrent() {}
         } payload;
         uint8_t checksum = 0;
     };
     #pragma pack(pop)

     #endif
     ```

Found it — and it's not a fault. It's a documented characteristic of the charger IC, and the numbers line up almost exactly.

**Netlist confirms the wiring is fine.** `V50_I` is isolated at night: `D2`'s cathode is on `V50`, anode on `V50_I`, so when the boost converter drives `V50` up from the battery, `D2` is reverse-biased and blocks that path. `R15` (the MAX809 reset pull-up) can only pull `V50_I` *down*, never up. AIN3 reads `V50_I` almost directly through `R1` (no divider) — so the ADC is reading the real net, not some other rail.

**The leak is inside `IC2`, the MCP73123 charger.** Its `VDD` pins (1/2) are wired straight to `V50_I`. The MCP73123 datasheet (§6.1, "Reverse‑Blocking Protection") states outright: *"Without \[reverse-blocking] protection, a faulted or shorted input would discharge the battery pack through the body diode of the internal pass transistor."* The chip has an internal PFET to block this, but it's not perfect — the datasheet specs a residual **"Battery Discharge Current / Output Reverse Leakage Current" (I_DISCHARGE)**: ~0.5 µA typ / 2 µA max in the "Charge Complete; No Battery; VDD ≤ V_STOP" condition, up to ~6–17 µA in Shutdown. That current flows from the battery, backward through the charger, out onto `VDD` — i.e. onto `V50_I`.

At night `V50_I` has essentially nothing else attached (just the ADC's high-impedance input through `R1`, and some caps). There's no load pulling it back to ground, so even a microamp-scale leak is enough to float that node up until it sits almost exactly at battery voltage. That's exactly what you're seeing: battery ~3.3V, `V50_I` ~3.35V — no diode drop, because it's a leakage-into-high-impedance situation, not forward conduction.

**Bottom line:**
- Not a wiring bug, not a firmware bug. Expected behavior of this charger IC when nothing is loading `V50_I`.
- Harmless — µA-scale, negligible compared to your sleep-current budget.
- Doesn't break your cloudy/low-power logic: `v50iCloudyThreshold = 4.5V` is well above this ~3.3–3.5V floor, so the existing `_lowV50IForSleep` check already correctly reads nighttime as "low power" — coincidentally correct, for the right underlying reason (no real panel output), just not for 0V.
- The one thing to internalize: `V50_I` will never read true 0V at night on this board — it has a floor near `VBAT`, not ground. Worth a one-line code comment if you want future-you not to re-panic over this, but no logic change needed.
