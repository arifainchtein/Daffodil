I've changed `Daffodil.ino` to read the new waterproof sensor over UART instead of using echo/trigger. **It hasn't been compiled**, because there's no `arduino-cli` on this machine, so please build it in the Arduino IDE.

**Wiring**
- Connect the sensor's **TX to GPIO 33**, the old ECHO wire.
- **GPIO 18 is no longer used by the sensor.** It stays free for tank1 in the trough + tank1 mode.
- Leave the sensor's RX pin unconnected. In UART auto mode it sends readings on its own.
- **Check the signal voltage:** GPIO 33 is not 5V-tolerant. If you power the sensor from 5V, its TX line will also be 5V, so either run the sensor on 3.3V or put a divider on that line. The old HC-SR04 echo had the same problem, so your board may already handle it.

**What changed in the code**
- I removed `NewPing`, the `sonar` object, and the `TRIGGER_PIN`/`ECHO_PIN` defines.
- New `beginUltrasonic()`: starts the ESP32's second hardware serial port (`Serial2`) at 9600 baud, receive-only, on pin 33. It uses a 1KB buffer so long WiFi uploads don't overflow it. It only starts in the modes that use the sensor: `DAFFODIL_WATER_TROUGH`, `DAFFODIL_SCEPTIC_TANK` and `DAFFODIL_WATER_TROUGH_TANK1`. In the flow and tank modes, pin 33 is left alone.
- New `readUltrasonicCm()`: reads the standard frame these sensors send (`0xFF, high byte, low byte, checksum`) and checks the checksum. It returns the newest distance in cm, with 0.1cm resolution. It doesn't block, which matters because `readSensorData()` runs every second.
- **"No reading" now shows as -99.** You get -99 if no valid frame has arrived for 5 seconds; NewPing used to return 0 instead.
- **`DAFFODIL_WATER_TROUGH_TANK1` now gets real trough readings.** It used to stay at -99 because the old sensor needed pin 18, which tank1 uses.
- I updated the pin table and known issues in `CLAUDE.md` to match.

**Not done**
- `DAFFODIL_2_WATER_TROUGH` (a second sensor on pin 18 filling `measuredHeight2`) is still a stub. It would reuse the same reading code on a second serial port, if you want it.
- The trough thresholds and the 90cm `MAX_DISTANCE` are unchanged. If the new sensor is mounted at a different height, re-check them with `SetTroughParameters`.

You don't need a 3.3V terminal or any extra resistor. I checked the KiCad netlist (`HardwareDesign/Daffodil/Daffodil.kicad_sch`), and the board already has what the probe needs on both sensor terminals:

| ESP32 pin | Level shifter | GPIO side | Terminal side |
|---|---|---|---|
| 33 | Q1 (2N7002) | R5 4.7k to 3.3V | R7 10k to V50 |
| 18 | Q2 (2N7002) | R6 4.7k to 3.3V | R8 10k to V50 |

The JP1/JP2 jumpers choose whether each terminal goes to the GPIO or to the ADS1115. For these sensors, set them to the GPIO side.

**What this means for wiring:**
- **DS18B20 water probe:** connect red to V50, black to GND, and the data wire to the pin-33 terminal. The DS18B20 runs fine anywhere from 3.0V to 5.5V. The 10k to V50 on the board is the pull-up the probe needs. It's weaker than the usual 4.7k but fine for a normal 1–3m probe cable. If you ever run a long cable and get -99 readings, add a 4.7k between data and V50 at the terminal.
- **Ultrasonic:** power it from V50 and connect its TX to the pin-18 terminal. My earlier warnings about 5V signals were wrong: the level shifters already make 5V safe on both pins.

**Code:** nothing functional changes. I only rewrote the two wiring comments in `Daffodil.ino` that said to add a 4.7k to 3.3V. I also saved this pin-18/33 wiring to memory so I don't repeat the warning next time.

I checked `Daffodil.ino` against the datasheet section and it matches. Yes, sensor **pin 4 (TX) goes to terminal 18**. The only exception is the Water Trough + Tank setting, where it goes to terminal 33.

| Datasheet | Code | |
|---|---|---|
| 9600 baud, 8 data bits, 1 stop bit, no parity | `begin(9600, SERIAL_8N1, rxPin, -1)` | ✓ |
| Frame `0xFF`, Data_H, Data_L, SUM | waits for the `0xFF` header, then reads 3 more bytes | ✓ |
| SUM = (0xFF + H + L) & 0xFF | `(frame[0] + frame[1] + frame[2]) & 0xFF` | ✓ |
| Distance = H × 256 + L, in mm | `(H << 8) \| L`, divided by 10 to give cm | ✓ |
| The sensor sends on its own; its RX pin only selects the output mode | only the ESP32's receive line is used, and the sensor's RX is left unconnected | ✓ |

Checked against the datasheet's own example, `FF 07 A1 A7`: the checksum works out to `0xA7`, and the distance is 1953mm, so `measuredHeight` would be 195.3cm.

**Wiring:**

| Sensor pin | Connect to |
|---|---|
| 1 VCC | V50 |
| 2 GND | GND |
| 3 RX | Leave unconnected |
| 4 TX | Terminal 18, with the cap on the 18 **Digital** header |

Leaving pin 3 unconnected is the mode you want. Per the datasheet, a floating or high RX gives the "processed", more stable reading every 100–500ms, while tying it low gives the raw real-time value every ~100ms. The firmware only marks a reading as missing (-99) after 5 seconds without a valid frame, so either rate works.

The one inaccuracy was that I'd described the update rate as "about every 100ms". I've corrected that comment in `Daffodil.ino` and the matching line in the technical manual. The user PDF never gave a rate, so it didn't need changing.
