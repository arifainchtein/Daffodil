So 3.3V now is mid-charge (LiFePO4's discharge curve is very flat, so voltage alone doesn't map cleanly to %, but 3.3V is comfortably "not empty, not full" — full/charge-termination is ~3.6V).

**On the 16mA vs 130mA question** — I don't think it's a sun/battery blend, and here's why: V50 is fed by two sources that are diode-OR'd, not blended:
- **D2** passes panel power straight through from V50_I when the panel is strong enough.
- **U5 (boost)** takes VBAT in and pushes it up to a fixed regulated output on V50, only when **MAX809L** (U6) detects V50_I has sagged below its ~4.63V threshold — and once boost is driving V50 to its regulated level, that reverse-biases D2, so the panel path drops out entirely.

It's a hard switch between "panel powers everything" and "battery powers everything," not a proportional mix. Given V50_I is reading ~3.4V right now (well under 4.63V), the boost is almost certainly active, which means **the battery should be supplying the entire V50 load right now — including during transmit — not just the difference.**

     ```cpp
     #define DIAGNOSTICRECORD_H

     // Generic on-demand diagnostics, triggered remotely via a RequestCommand
     // ("EnableDiagnostics#<type>" / "DisableDiagnostics") — NOT part of the normal periodic
     // uplink. diagnosticType selects which member of the payload union is populated; add new
     // diagnostic kinds by adding a payload struct + union member + DIAGNOSTIC_TYPE_* constant,
     // not a new top-level LoRa packet type/size.
     #define DIAGNOSTIC_TYPE_NONE        0
     #define DIAGNOSTIC_TYPE_TX_CURRENT  1

     #define DIAGNOSTIC_TX_MAX_SAMPLES 20

     #pragma pack(push, 1)
     struct TxCurrentSample {
         uint16_t offsetMs;    // ms since LoRa.beginPacket()
         uint16_t milliamps;   // INA219 current_mA at that offset
     };

     struct TxCurrentDiagnosticPayload {
         uint16_t v50i_mV;     // V50_I sampled just before keying up, millivolts
         uint16_t mAPre;       // battery current just before keying up
         uint16_t mAPost;      // battery current just after TX completed
         uint8_t  sampleCount; // valid entries in samples[]
         TxCurrentSample samples[DIAGNOSTIC_TX_MAX_SAMPLES];
     };

     // Total size: 4 (totpcode) + 8 (serialnumberarray) + 1 (diagnosticType)
     //           + 87 (payload union, sized to TxCurrentDiagnosticPayload) + 1 (checksum) = 101 bytes.
     // Must stay unique relative to other LoRa packet structs (DigitalStablesData, RequestCommand,
     // WeatherForecastUpdate, GraveyardShiftUpdate) since receivers dispatch on packet size.
     struct DiagnosticRecord {

         uint8_t serialnumberarray[8];
         uint8_t diagnosticType = DIAGNOSTIC_TYPE_NONE;
         union DiagnosticPayload {
             TxCurrentDiagnosticPayload txCurrent;
             DiagnosticPayload() : txCurrent() {}
         } payload;
         uint8_t checksum = 0;
     };
     #pragma pack(pop)

     #endif
     ```

**Netlist confirms the wiring is fine.** `V50_I` is isolated at night: `D2`'s cathode is on `V50`, anode on `V50_I`, so when the boost converter drives `V50` up from the battery, `D2` is reverse-biased and blocks that path. `R15` (the MAX809 reset pull-up) can only pull `V50_I` *down*, never up. That current flows from the battery, backward through the charger, out onto `VDD` — i.e. onto `V50_I`.

At night `V50_I` has essentially nothing else attached (just the ADC's high-impedance input through `R1`, and some caps). There's no load pulling it back to ground, so even a microamp-scale leak is enough to float that node up until it sits almost exactly at battery voltage. That's exactly what you're seeing: battery ~3.3V, `V50_I` ~3.35V — no diode drop, because it's a leakage-into-high-impedance situation, not forward conduction.

- Not a wiring bug, not a firmware bug. Expected behavior of this charger IC when nothing is loading `V50_I`.
- Harmless — µA-scale, negligible compared to your sleep-current budget.
- Doesn't break your cloudy/low-power logic: `v50iCloudyThreshold = 4.5V` is well above this ~3.3–3.5V floor, so the existing `_lowV50IForSleep` check already correctly reads nighttime as "low power" — coincidentally correct, for the right underlying reason (no real panel output), just not for 0V.

A union is a type where all its members share the exact same memory address — the compiler allocates space for only the *largest* member, and every member is just a different way of interpreting those same bytes. Contrast with a struct, where each field gets its own separate space and the struct's size is the sum of its members (plus padding).

**Applied to `DiagnosticPayload`:**

```cpp
union DiagnosticPayload {
    TxCurrentDiagnosticPayload txCurrent;   // 87 bytes
    I2CStatusDiagnosticPayload i2cStatus;   // 1 byte
    DiagnosticPayload() : txCurrent() {}
} payload;
```

`txCurrent` and `i2cStatus` aren't two separate storage locations — they're two different *lenses* onto the same 87-byte block, both starting at the same address. `sizeof(DiagnosticPayload)` is 87 (the size of the biggest member), not 88. When you write `payload.i2cStatus.deviceFoundMask = buildI2CStatusMask();`, you're writing 1 byte into the front of that 87-byte block; the other 86 bytes are just sitting there unused for this diagnostic type but still get transmitted, since `DiagnosticRecord`'s total size never changes based on which member you populated.

**Why the union alone isn't enough — the discriminator byte:**

Memory doesn't remember which member you last wrote. If you write `payload.i2cStatus` and I only had `payload` itself, I couldn't tell whether those bytes mean "1 mask byte + 86 bytes of garbage" or "87 bytes of a real TX-current sample dump." That's exactly why `DiagnosticRecord` carries `diagnosticType` as a sibling field, outside the union:

```cpp
struct DiagnosticRecord {
    ...
    uint8_t diagnosticType;   // the "which lens is valid" tag
    union DiagnosticPayload { ... } payload;
    ...
};
```

This is the standard **tagged union** pattern. The union gives you compact, reusable storage; the tag tells the reader how to interpret it. Concretely, in `loop()` right now:

```cpp
diagRecord.diagnosticType = DIAGNOSTIC_TYPE_I2C_STATUS;
diagRecord.payload.i2cStatus.deviceFoundMask = buildI2CStatusMask();
```

vs. the TX-current path a few lines above it:

```cpp
diagRecord.diagnosticType = DIAGNOSTIC_TYPE_TX_CURRENT;
diagRecord.payload.txCurrent = pendingTxDiagnostic;
```

Both branches build the exact same `DiagnosticRecord` type and both get sent through `sendMessage()` unchanged — same size, same wire format. Whoever receives it (eventually Annabelle) reads `diagnosticType` *first*, and only then decides whether to interpret `payload` as `.txCurrent` or `.i2cStatus`. Reading the wrong one would just reinterpret the same bytes as the wrong struct — no crash, just nonsense output, so the tag is load-bearing, not optional.

**Why this shape at all, instead of just two separate structs:** because `processLora()` dispatches incoming packets by `packetSize == sizeof(StructType)` (see `DigitalStablesData.h`'s "must stay unique" comments) — if `TxCurrentDiagnosticPayload` and `I2CStatusDiagnosticPayload` were two independent top-level packets, they'd need two different, carefully-managed unique sizes, and every future diagnostic type would need yet another unique size. The union collapses all diagnostic kinds into one fixed-size packet shape, and `diagnosticType` does the dispatching instead of size. The cost, which you accepted early on, is that a tiny 1-byte payload like I2C status still rides inside the ~101-byte envelope sized for the biggest diagnostic (`TxCurrentDiagnosticPayload`) — wasted airtime, acceptable because diagnostics are on-demand and rare, not periodic traffic.

**One more detail worth knowing — `DiagnosticPayload() : txCurrent() {}`:** this constructor exists so that a freshly-created `DiagnosticRecord` has its union zero-initialized (value-initializing `txCurrent`, the largest member, zeroes the whole 87-byte block it occupies) rather than containing whatever garbage was already sitting in RAM. That matters here specifically: when you populate the small `i2cStatus` member, only its 1 byte gets overwritten — without this constructor, the other 86 bytes would be leftover stack garbage getting transmitted over LoRa instead of deterministic zeros.
