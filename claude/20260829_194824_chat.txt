That "Pulse and Sleep" display on the dashboard is `OPERATING_STATUS_CLOUDY` (Daffodil.ino:2868-2871) — it forces the sleep-between-LoRa-pulses behavior even when solar efficiency is theoretically fine. It gets set whenever **any one** of four independent checks says "cloudy" (line 2797, an OR — no cross-corroboration needed):

1. **`luxSaysCloudy`** — lux between 30 and **10000**
2. **`v50iSaysCloudy`** — V50_I voltage below 3.5V
3. **`panelCurrentSaysCloudy`** — panel current below 15mA
4. **`forecastSaysCloudy`** — cached OpenWeatherMap forecast cloudiness ≥70%, only checked if fetched within the last 31 min — this one isn't even a live reading

Given what you're describing — charging at 328mA (way above the 15mA panel-current threshold) — #2 and #3 should both be reading "not cloudy" right now, so that rules those out.

That leaves the two live-but-unverified suspects:
- **`luxCloudyThreshold = 10000`** — this is very aggressive. Full direct sun is 30,000-100,000+ lux, but if the BH1750 is behind an enclosure/diffuser or not angled straight up, it can easily sit under 10,000 lux even at noon in clear sun. Notably, the other two thresholds (v50i, panelCurrent) were *already* lowered on 2026-07-24 after field data showed them false-triggering CLOUDY in clear midday sun on this exact device (TopTank) — lux never got the same recalibration pass.
- **Stale forecast** — if OpenWeatherMap said cloudy for this hour earlier this morning and it's since cleared up, `forecastSaysCloudy` stays true for up to ~31 min after the last fetch regardless of actual sky conditions.

Can you check the dashboard (or run `printCurrentDSDData` over serial) for the current `lux` value and whether weather data is "fresh"? That'll tell us which of the two is firing. If it's lux, the fix is the same kind of threshold recalibration already done for v50i/panelCurrent — I'd want a real reading from this device in clear sun before picking a new number, rather than guessing.

That's not a firmware bug this time — it's working as designed, just against a config that doesn't fit bench testing.

**What happened:** The config switch is reading `cswOutput=4567`, which falls in the `4391-4698` band → `FUN_1_TANK` with **solar mode ON** (`usingSolarPower=true`, per the "11001, solar on" row at Daffodil.ino:1488-1492). So this unit is treated exactly like a deployed solar-powered TANK node, not a bench-test unit.

With `usingSolarPower=true`, all the solar-based sleep protections engage — including the CLOUDY check we just fixed for TopTank. On the bench, `panelCurrent` is bouncing around 1.8-60mA (no real panel attached, just ambient/noise on the INA219Solar input), and it dipped to `1.80mA` — well under the `15mA` cloudy threshold — so `panelCurrentSaysCloudy` correctly fired, `operatingStatus` went to `CLOUDY (4)`, and the device deep-slept exactly as it's supposed to for a solar unit that thinks it has no sun. The log confirms this precisely: `line 2609 isSleepMode=true because of is cloudy ... operatingStatus=4`.

**Fix is a config change, not a code change:** flip the dip switch's solar bit to the "solar off" position for this `FUN_1_TANK` slot (band `8728-8937`, per the table at line 1433-1437) — that sets `usingSolarPower=false`, which disables every sleep/COMMA/cloudy check so the device stays awake while tethered.

One thing to flag from the [[project_daffodil_battery_failures]] history: if the battery is still connected to the screw terminals during this bench session, running with `usingSolarPower=false` disables all over-discharge protection too — that combination (USB-tethered + battery attached + solar-off) is exactly what killed a battery before. Disconnect the battery from the screw terminals before flipping to solar-off, or keep it connected only if you're fine with no low-voltage protection during the test.

This is unrelated to any of the CLOUDY/sleep fixes — it's a different, intentional protection: `OPERATING_STATUS_COMMA`, the critically-low-battery cutoff (Daffodil.ino:1712, `commaVoltage = 2.80`). Since `rtc_comma_mode` persists in RTC memory across sleep, from here it'll recheck every **10 minutes** (line 1123-1126) rather than doing a full boot each time, until voltage clears the threshold.
