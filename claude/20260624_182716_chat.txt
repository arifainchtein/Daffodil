Good challenge — here's the honest answer:

The only real reason to have two structs is **storage efficiency** — `CommaRecord` stored to flash doesn't need `totpcode`, `index`, `total`, or `checksum`, so those 7 bytes would be wasted per record × 650 = ~4.5KB of zeros on flash. But with LittleFS on ESP32 with a 1MB+ filesystem, that's negligible.

Against that, you get: simpler code (no copy/wrap step), one mental model, fewer bugs. That tradeoff clearly favours one struct.

The merged design, with serialnumber added:

```c
#pragma pack(push, 1)
struct CommaRecord {
  uint32_t time;           // Unix-seconds of reading
  float    voltage;        // battery voltage
  char     devicename[8];  // device short name
  uint8_t  serialnumber[8];// device serial number
  long     totpcode;       // TOTP auth (0 when stored, set before LoRa send)
  uint8_t  index;          // 0-based batch position (set before LoRa send)
  uint8_t  total;          // total records in batch (set before LoRa send)
  uint8_t  checksum;       // XOR checksum (set before LoRa send)
};
#pragma pack(pop)
// sizeof = 4+4+8+8+4+1+1+1 = 31 bytes on ESP32
```

31 bytes is unique vs all existing LoRa packet sizes (19, 37, 164, and DigitalStablesData which is 200+).

The `index`/`total` fields feel like batch metadata but in practice every record you send already *is* one packet, so knowing its position in the sequence belongs on the record. When stored, those bytes are just 0 — harmless.

## What's working
- **Annabelle sends correctly**: `Annabelle.ino:1049-1080` triggers every 5 minutes (`minute % 5 == 0`), downloads from OpenWeatherMap if internet is up, builds a `WeatherForecastUpdate` (4 forecasts + TOTP), and calls `sendMessage()`.
- **Daffodil's dispatch is correct**: `Daffodil.ino:526-540` matches on `sizeof(WeatherForecastUpdate)`, validates the TOTP code, and calls `weatherForecastManager->saveForecasts(weatherForecastUpdate.forecasts)`.
- **Radio config matches** on both ends (433MHz, SF9, BW125kHz, same sync word default).
- **TOTP scheme is a shared network-wide secret** (not per-device-pair), so that's not a v1 vs v2 mismatch issue — though it does depend on RTC clock sync between the two devices (worth checking if either device's time has drifted).

## The bug
`WeatherForecastManager::saveForecasts()` (`WeatherForecastManager.cpp:164-180`) is declared and implemented to take **8** `WeatherForecast` elements — `memcpy(forecasts, newForecasts, sizeof(WeatherForecast) * 8)`, i.e. it always reads/writes 320 bytes.

But the LoRa-transmitted struct only carries **4** forecasts (`WeatherForecastUpdate.forecasts[4]` in `SolarPowerData.h:23` — kept at 4 instead of 8 specifically to fit LoRa's payload size limit).

So `Daffodil.ino:533` calls `saveForecasts(weatherForecastUpdate.forecasts)` with only a 4-element (160-byte) array, and `saveForecasts()` reads 320 bytes from it — a **160-byte stack over-read** past the end of the local `weatherForecastUpdate` variable in `processLora()`, every single time Daffodil receives a forecast packet. The first 4 slots (`forecasts[0..3]`, including the one actually used for the cloudy check, `forecasts[0].cloudiness`) get the correct data, but slots `[4..7]` get garbage stack memory, and that garbage also gets written to NVS via `preferences.putBytes()`.

This is the only call site affected — Annabelle's own `downloadWeatherData()` (`WeatherForecastManager.cpp:159`) correctly passes its real 8-element member array.

This bug doesn't fully explain "not receiving at all" (since forecast[0] — the one Daffodil actually reads — is correctly copied), but it is definite undefined behavior on every reception, and on ESP32 stack overreads of this size can occasionally trigger crashes/resets depending on stack layout, which **would** look like "never receiving" if it crashes before the debug log prints.

## Recommended next steps
1. **Fix the over-read**: add a `saveForecasts(const WeatherForecast newForecasts[], int count)` overload (or change the existing one to take a count) so Daffodil's 4-forecast LoRa packet doesn't get read as 8. This is in the shared library, so it'd affect both Annabelle and Daffodil builds.
2. **Confirm with live debug serial** (`debug#1` on both devices) whether Daffodil ever logs `" Receive and processed weatherForecast "` (success) or `" Receive WeatherForecastUpdate but invalid code"` (TOTP/clock-drift rejection) — that tells us definitively whether packets are arriving at all vs. being rejected vs. corrupting the device.

     f) **`quickReadBusVoltage()` median-filtered** (originally lines 862-870):
     ```cpp
     // Before:
     float quickReadBusVoltage() {
       Wire.beginTransmission(0x41);
       Wire.write(0x02);  // INA219 bus voltage register
       if (Wire.endTransmission() != 0) return -1;
       Wire.requestFrom(0x41, 2);
       if (Wire.available() < 2) return -1;
       uint16_t raw = ((uint16_t)Wire.read() << 8) | (uint8_t)Wire.read();
       return (int16_t)((raw >> 3) * 4) * 0.001f;  // identical to getBusVoltage_V()
     }
     // After:
     // A single I2C sample is vulnerable to a bus glitch, and this reading directly
     // gates COMMA/sleep decisions (a bad low sample causes a real deep-sleep +
     // false COMMA log entry — see e.g. a spurious 1.55V sample that triggered
     // COMMA mode overnight). Take several samples and use the median to reject
     // one bad reading; failed individual reads are skipped rather than aborting.
     float quickReadBusVoltage() {
       const int CSW_SAMPLES = 5;
       float readings[CSW_SAMPLES];
       int validCount = 0;
       for (int i = 0; i < CSW_SAMPLES; i++) {
         Wire.beginTransmission(0x41);
         Wire.write(0x02);  // INA219 bus voltage register
         if (Wire.endTransmission() != 0) continue;
         Wire.requestFrom(0x41, 2);
         if (Wire.available() < 2) continue;
         uint16_t raw = ((uint16_t)Wire.read() << 8) | (uint8_t)Wire.read();
         readings[validCount++] = (int16_t)((raw >> 3) * 4) * 0.001f;  // identical to getBusVoltage_V()
       }
       if (validCount == 0) return -1;
       for (int i = 1; i < validCount; i++) {
         float key = readings[i];
         int j = i - 1;
         while (j >= 0 && readings[j] > key) {
           readings[j + 1] = readings[j];
           j--;
         }
         readings[j + 1] = key;
       }
       return readings[validCount / 2];
     }
     ```

how do i apply a know load

--- CLAUDE ---


--- CLAUDE ---
With just a multimeter, the simplest practical method is a single power resistor as your "known load" — no special equipment needed.

**1. Pick a resistor**
For a single-cell LiFePO4 at ~3.2V nominal, aim for a test current well under the cell's rated 0.3C (180mA for a 600mAh cell) — don't stress it further while it's already suspect. A **33Ω resistor** gives you roughly `3.2V / 33Ω ≈ 97mA`, a sensible test point. Power dissipated is `I²R ≈ 0.097² × 33 ≈ 0.31W`, so use at least a **1-2W resistor** for margin (anything rated much less than that will run hot). Standard through-hole resistors in the 22-47Ω range will all work fine — exact value doesn't matter, you'll just plug in whatever you actually use.

**2. Measure open-circuit (rest) voltage first**
Nothing connected, let it sit a few seconds, read the voltage across the terminals. Call this **V_open**.

**3. Connect the resistor and measure under load**
Two ways to do it, in order of preference:
- **Best, if your meter does current:** put the multimeter in series (mA/A jack) between the battery and the resistor, so you read actual current directly — call it **I**. Separately note the voltage across the battery terminals at that same moment (a second meter helps here, or just do it fast since the reading won't drift much in a few seconds).
- **Simpler, one meter:** just connect the resistor across the terminals and measure the voltage across the battery *while loaded* — call this **V_loaded**. Then compute current from Ohm's law: `I = V_loaded / R` (using your resistor's actual value).

**4. Compute internal resistance**
```
R_internal = (V_open − V_loaded) / I
```
Compare against the spec: ≤120mΩ (0.12Ω) for a healthy cell. If you get something like 1Ω or more, that's a clearly damaged cell.

**For the separate rest-voltage recovery test** (the other one from before), you don't need a load at all — just let it charge in the sun, then disconnect/cover the panel, wait a couple of minutes unloaded, and read it directly.

Good question — the answer is circuit topology, not magic.

The INA219 sits **in series with the battery on the battery rail**. It measures current flowing in or out of the battery specifically. The solar panel injects current from the **other side** — into the load rail — so the INA219 never directly "sees" solar current. What it sees is the **net result**:

```
Solar panel → [load rail] ← Battery (via INA219)
                   ↓
               Device load
```

So the INA219 reading equals:

```
INA219 = load_current − solar_current
```

Which means:
- **Positive reading** → battery discharging (load > solar, battery making up the difference)
- **Negative reading** → battery charging (solar > load, excess flows into battery)
- **Zero** → solar exactly equals load

You can see this clearly in the data:
- **All night (no solar):** INA219 = +110mA → total device load is ~110mA, all from battery
- **13:44 (midday solar on damaged battery):** INA219 = **-130mA** → solar was delivering 130mA MORE than the load needed, charging the battery at 130mA
- **14:10–14:26 (solar and load balanced):** INA219 hovering near 0 (−19mA, +6mA, −1mA) → solar ≈ load
- **09:22 this morning:** INA219 = +53mA → battery still discharging at 53mA

So at 09:22, I was actually slightly loose with "roughly matching" — more precisely: if the device load is still ~110mA (same as at night), then solar is supplying **~57mA** and battery makes up the remaining 53mA. Not balanced yet, but solar is already cutting the battery discharge rate in half vs. the night. As the sun rises higher you'd expect the INA219 to drift toward zero and then go negative (battery actively charging).

The -130mA reading at 13:44 yesterday is actually a great sanity check that the math works — that's the solar panel in full afternoon sun with a nearly-empty battery, pumping 130mA more than the device needs.

Exactly right on both counts.

**The -20 to +20mA band:** Yes — anything in that range means solar is roughly covering the load. Whether it's "enough" depends on what you need:
- **For sustained operation:** you need the *average* over a full day to be zero or negative (net charging during daylight replenishes what the night discharged)
- **For just not dying right now:** anything ≤ 0 means the battery isn't being depleted at that moment

So -20mA is actually better than 0mA — it means the battery is slowly recovering. The goal for a day cycle is: deeply negative (charging hard) in the afternoon, crossing zero at dusk, mildly positive (discharging slowly) all night, then crossing zero again after sunrise.

**The Wally USB current sensor:** Yes, that's a much better instrumentation setup. Right now with just the INA219 you only know the net result (load minus solar). With a current sensor on the solar input you get **both sides of the equation directly:**

```
Solar current (USB sensor) → known
Battery net current (INA219) → known
Total device load = solar + battery_discharge (or solar − battery_charge)
```

What you can't see today is: if the INA219 shows 0mA, is that because the load is 10mA and solar is 10mA, or load is 200mA and solar is 200mA? Those look identical on the INA219 alone. The USB sensor breaks that ambiguity — you'd know exactly how much the panel is delivering and exactly what the device is consuming, independently.

It would also let you catch things like a partially shaded panel delivering only 20mA when it should be giving 300mA — right now you'd see that as a higher-than-expected positive INA219 reading and have to infer why.
